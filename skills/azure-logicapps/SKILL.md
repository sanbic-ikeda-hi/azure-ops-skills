# Azure Logic Apps の運用

## 認証と対象

開始時にヘルパーのGet-UserSettings.ps1で保存情報と不足項目を確認する。必要な不足分だけチャットで質問し、接続ファイルや生成済みIDで分かる項目は聞き直さない。保存の形式・タイミングは共通認証手順の「ユーザー固有情報の確認と保存」に従う。
登録済みの別名から完全IDを解決し、曖昧なら候補から選んでもらう。RG・リソース・Sandbox条件は登録を指示されたものだけSet-UserSettings.ps1で保存する。保存情報は接続先・許可範囲・操作承認を変更しない。不一致は自動修正せず止め、変更前は対象・Consumption／Standard・所在地・関連IDを再取得して照合する。

Windows / PowerShell 7.2以降、Az.Accounts・Az.Resources、専用アプリの接続プロファイルとユーザー証明書を使う。導入・設定変更はユーザーが行う。

Azure操作前に共通認証手順を読む。ソースではリポジトリの `docs/authentication.md`、配布先ではこのSKILL.mdの隣の `references/authentication.md` を使う。同じ作業中に既読で変更がなければ、毎回全文を読み直す必要はない。

- 接続は専用アプリの証明書認証。接続時・各API呼び出し前の照合を維持し、管理者へ自動切替しない。
- Azure操作は証明書を使えるWindowsユーザーの環境で正規の承認付き実行を行う。隔離ユーザーへの証明書共有や秘密鍵ACL拡張はしない。
- 初回作成・権限付与解除はユーザー実行。今回の対象サブスクリプションと完全なリソースIDを照合し、別案件の対象を引き継がない。
- SandboxはPC側のsandboxSubscriptionIdで確認する。本番へ試験を向けず、試験の対象・費用・影響を具体化する。
- 秘密値・生レスポンス・Debug・Transcriptを出力・保存しない。

## Microsoft製スキルとの連携

このスキルをサービス別の入口とし、次の条件に合うときだけMicrosoft製スキルの技術手順を参照する。基本一覧の取得だけなら追加スキルは不要。

| 依頼 | 参照先 | 適用範囲 |
| --- | --- | --- |
| Consumption / Standardの棚卸し、タグ検索 | `azure-resource-lookup` | 基本一覧は既存ヘルパーを優先。Microsoft.Logic/workflowsとMicrosoft.Web/sitesのworkflowappを区別する |
| StandardのWebホスト、共有プラン、ネットワークの障害調査 | `azure-diagnostics` | 導入版とMicrosoft Learnで適用可能と確認できたApp Service基盤の手順だけを参考にする。Functions固有の手順を流用しない |
| ワークフロー、コネクタ、トリガー、実行履歴の調査 | Microsoft Learn MCP | Logic Apps向けの公式手順と必要権限を確認する。該当するMicrosoft製スキルがなければ、他サービス用で代用しない |

`azure-reliability`と`azure-upgrade`をLogic Appsへ自動適用しない。Standardのkindにfunctionappが含まれても、Functionsのプラン移行やトリガー操作の対象にはしない。

### 参照から実行へ進む条件

1. 利用可能なスキル一覧から名前を照合し、表示された実際のSKILL.mdと必要な参照ファイルだけを読む。導入版の対応サービス・前提条件を確認し、使用したスキル名と版（なければ参照パス）を案件に記録する。Microsoft製の全文をこのスキルへ複製しない。
2. 未導入、未対応、必要なツールがない場合は明示し、Microsoft Learn MCPで技術手順を補う。依存スキル、Azure CLI、拡張機能などを自動インストール・更新しない。必須環境の不足や認証・権限エラーを別の認証で回避しない。
3. 参照先のスクリプトは、実行前にログイン、Azureへの書き込み、権限付与、削除、秘密値出力、自動再試行の有無を確認する。調査・設計の依頼では読み取りと提案までに留める。他スキルの参照は操作の許可を追加しない。
4. Azureへの実行には既存のPowerShellヘルパーとCommon.ps1の接続・照合処理を優先する。追加コマンドでも、実行前に専用アプリのID・認証種別・テナント・明示したサブスクリプションを照合し、変更先の完全なリソースIDを確認する。CLI・azd・MCPがPowerShellと同じ認証を使うとは仮定しない。そのツールの接続主体を照合できなければ実行せず、確認方法を案内する。別ツールのために秘密鍵を取り出さない。
5. 参照先が管理者ログインやContributorを前提としていても、同意済みの個別リソース権限の方針を維持する。不足する操作と対象IDを特定し、ユーザー向けの付与・解除コマンドを準備する。Storage・監視ログなどの追加読み取り権限も、現在のロールに含まれると仮定しない。参照先の自動修復・再試行を理由に、権限拡大や削除を行わない。
6. 新規作成や変更の案は、このスキルの「新規作成」「既存変更」の手順に戻してレビューする。初回作成は既存RG・新規RGのどちらでもユーザーが実行する。参照した手順が、対象・権限・秘密情報の制約と両立しなければ実行を止め、具体的な代替手順を示す。

デプロイの検証・実行手順が必要な依頼では、`azure-validate` / `azure-deploy`も参照できる。ただし、導入版が対象サービス・方式に対応し、準備済み計画などの前提を満たす場合に限る。実行にはユーザーの依頼範囲と上記の接続・権限確認が必要。前提がない通常の調査や新規作成を、自動で`azure-prepare`→検証→デプロイへ連鎖させない。未実施の検証をValidated扱いにしない。

## 読み取り

初回設定済みなら、対象サービスの全リソースを読み取り対象にできる。依頼された内容に必要な範囲を取得する。
ユーザー共通の配置済みスキルでは、このSKILL.mdの隣の scripts/Get-ServiceInventory.ps1 を使う。
ソースリポジトリで作業中はリポジトリ直下の scripts/Get-ServiceInventory.ps1 を使う。

~~~powershell
# <HELPER_PATH> は確認した絶対パスに置換する。現在の作業ディレクトリから推測しない。
pwsh -NoProfile -File '<HELPER_PATH>\Get-ServiceInventory.ps1' -Service LogicApps -SubscriptionId '<SUBSCRIPTION_ID>' -OutputMode Summary -OutputPath '<NEW_RESULT_PATH>.txt'
~~~

要約は既定20件。取得範囲・TotalCount・Count・ReturnedCount・DisplayTruncatedを区別し、全結果はリポジトリ外の新しい絶対パスへ保存する。RGが分かる場合は-ResourceGroupNameを指定する。3サービスをまとめる依頼だけ-Service Allを使う。
追加表示は同じscriptsのGet-InventoryReport.ps1 -Path '<SAVED_RESULT_PATH>.txt' -Skip 20 -Limit 20を使い、Azureへ再接続しない。Source=SavedReportと取得日時を示し、変更前は対象を再取得する。詳細な取得・表示方針は共通手順の「読み取りと候補の選択」に従う。

ヘルパーは一覧と基本メタデータのみ。詳細が必要なら、導入済みモジュールの版とMicrosoft LearnでAPI・必要権限を確認する。
読み取りロールには秘密を取得する操作を含めない。不足する権限は理由を添えてユーザーに案内し、自動追加しない。
取得日時・接続先・成功/未取得を分ける。失敗を「0件」「設定なし」に置き換えず、キャッシュやIaCを現在の実環境と扱わない。

## 対象選択と権限相談

詳細が必要なら `Get-ServiceDetails.ps1` に個別IDと必要な `-Section` を指定する。Consumptionの構造要約はStructure、Standardのアプリ関連はOverview,Identity,Planを使う。説明はソースの `docs/service-operations.md`、配布先の `references/service-operations.md` を必要時に読む。ワークフロー本文・式・接続値を会話へ出さない。

操作を許可する対象を探す、キーワードで絞る、必要な権限を相談する依頼では、まず「何をしたいか」を確認し、サービス別の一覧から候補を示す。既に明確な目的・対象は聞き直さない。
対象選択や権限提案の前に共通手順を読む。ソースリポジトリではルートの `docs/change-workflow.md`、配布済みスキルではこのSKILL.mdの隣の `references/change-workflow.md` を使う。カレントディレクトリから場所を推測しない。

~~~powershell
pwsh -NoProfile -File '<HELPER_PATH>\Get-ServiceInventory.ps1' -Service LogicApps -SubscriptionId '<SUBSCRIPTION_ID>' -Keyword 'orders' -OutputMode Summary -OutputPath '<NEW_RESULT_PATH>.txt'
~~~

`-Keyword` は名前・リソースグループ名の部分一致。`-ResourceGroupName` でRGの完全一致も指定できる。検索なしならサービスの一覧を提示する。
番号と完全なリソースIDを対応させ、ユーザーに対象を選んでもらう。候補の選択だけを権限付与・変更の承認とは扱わない。
目的に必要な操作、追加権限、実際に許可される範囲、影響、解除のタイミングをAIが提案する。詳細調査の読み取り権限も確認し、既存変更・新規作成の手順へ進む。

## 既存変更

共通の定型変更ヘルパーはリポジトリの `scripts/Invoke-ServiceOperation.ps1`。ConsumptionのEnable/Disableだけに対応し、Standard全体や個別ワークフローへ流用しない。計画ファイルを確認してから実行する。対応範囲と検証状況は上記の共通参照文書に従う。

1. 完全なリソースID、現状、変更前後、影響、費用への影響、戻し方を準備する。
2. 必要なAPI操作を列挙したカスタムロールと、そのリソースだけへの割当コマンドを用意する。
3. 共通手順の「許可内容のアドバイス」に従い、実行依頼の本文で、専用アプリのサービスプリンシパルへのAzure RBAC割当であること、付与先ID、対象、追加操作と意味、影響・有効期間・解除方法を説明する。Sandboxでも省略せず、その後に権限管理ができるユーザーによる実行を案内する。
4. コマンドにはテナントID、サブスクリプションID、専用アプリのサービスプリンシパルObjectId、RoleId、完全なScopeを入れる。
5. サブスクリプション/RG全体の変更権限、Owner/Contributorへの丸ごとの昇格を通常の手順にしない。関係する別リソースは個別に案内する。
6. 権限反映後、専用アプリ接続で承認済み変更を適用する。共通手順の「変更後の検証と復元」に従い、各操作後のGETで状態・変更値・維持する設定を照合し、ワークフローの動作確認は実施した範囲を別に記録する。
7. 終了・中断時には今回新規追加した割当だけの解除コマンドを案内する。元の読み取り権限は残す。

削除、ロール割当の自動追加、ロック解除、管理者への自動認証切替はしない。
NotActionsは別ロールから与えられた権限を取り消すものではない。残存・継承された変更権限を確認する。
認証・権限・ネットワーク・環境の失敗は直ちに報告し、失敗した操作と依存する変更を止める。共通手順の停止境界に従い、許可済みで独立した読み取り・ローカル調査は継続できる。同じ拒否要求や設定変更を自動再試行せず、既定の修正回数の停止規則を維持する。

## 新規作成

リソース作成も必須の対応用途とする。共通手順の「新規作成」「作成失敗の診断」に従い、よく使う手順と再利用できる作成・診断ヘルパーをスキルと一緒に維持する。試験専用の固定名や実環境IDは共通化しない。
既存RG・新規RGともユーザー指定を尊重する。新規RGは必須にしない。
全作成リソースのIDと依存関係、同名の有無、費用、接続先への影響を先に確認する。
最初の作成は、ユーザーが実行する具体的なコマンド/IaCを準備する。同名があれば停止し、既存を上書きしない。
その後、新しく作った各リソースだけに必要権限を付けるコマンドを案内し、設定・配置・検証を専用アプリで進める。
作成権限と更新権限を区別できないAPIがある。RG全体の権限を「新規作成だけ」と説明しない。
What-if等は差分確認の補助であり、未評価項目や外部への副作用を完全に防ぐ保証ではない。

## このサービス固有の確認

ConsumptionはMicrosoft.Logic/workflows、StandardはMicrosoft.Web/sitesのkind=workflowappとして区別する。Standardがfunctionappも含むkindを持つ場合はLogic Appsを優先する。接続リソース、マネージドID、自動トリガー、実行対象への影響を確認する。実行履歴本文・定義内の秘密値・署名付きコールバックURL・接続資格情報を出力しない。作成・有効化・再送信で業務処理が実行される可能性を計画に含める。

Consumptionの有効化・無効化だけが目的なら、対応する操作APIを使い、定義全体の更新権限をまとめて要求しない。操作後はGETで状態を確認し、定義・接続先等の意図しない変更がないことを出力しないメモリ内比較で確認する。試験終了時の状態は開始前に決め、元がDisabledなら復元もGETで確認する。

有効・無効の状態確認と、トリガーを呼び出す実行試験を分ける。状態確認のためだけにコールバックURLを取得したりHTTPトリガーを呼び出したりしない。外部処理や自動実行がない試験用ワークフローでの成功を、業務ワークフローやStandardの検証済みとして扱わない。

## 案件への記録

対象・変更案・IaC・結果は現在の案件に保存する。共通スキルのソースやGitには実環境の生データを入れない。
コード/ローカル検証、ユーザー提供の実行結果、独立したAzure実取得を分けて報告する。
検証状況は対象・時点・実行主体とともに記録し、その範囲を越えて検証済みと扱わない。ローカルテストの成功だけで本番利用を検証済みとしない。
試験では共通手順の「Sandboxでの試験」に従い、計画・結果をUTF-8の新規テキストへ保存し、復元・権限解除・後片付けの確認範囲を残す。
