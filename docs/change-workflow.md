# 変更・新規作成の共通手順

サービスごとのスキルからこの方針で作業します。具体的なAPIと必要権限は作業時の導入バージョンとMicrosoft Learnで確認します。

## 既存リソースの変更

1. 専用アプリの読み取り接続で、現在の設定・親子リソース・共有プラン・接続先を把握する。
2. 対象の完全なリソースID、変更前後、影響、費用が変わる場合の見込み、戻し方を提示する。秘密値は表示しない。
3. 必要なAPI操作だけを持つカスタムロールと、対象リソースだけへの割当コマンドを準備する。
4. 「対象でロール定義・割当を管理できるアカウントでサインインして、このコマンドを実行」とユーザーに案内する。
5. 管理者向けコマンドにはテナント・サブスクリプション・専用アプリのサービスプリンシパルObjectId・ロール・Scopeを明記する。
6. サブスクリプションやRGを変更権限のScopeにしない。関連Storage・App Serviceプラン等が必要なら個別に理由とIDを示す。
7. 権限反映後、専用アプリ接続で同意済みの変更だけを適用し、実取得と動作で確認する。
8. 今回作成したロール割当を記録し、その割当だけを解除するユーザー向けコマンドを示す。失敗・中断時も残った割当を報告する。

ロールのAssignableScopesは「そのロールを割り当てられる場所」であり、アクセスを与えるScopeとは別です。
ロールの定義を作っただけでアクセスは付与されません。権限レビューでは実際のロール割当のScopeを確認します。
既存ロールを無断で更新しません。カスタムロールの変更は他の割当に影響する場合があります。
リソース単位の権限で実行できない手段では、自動で権限を広げず、より限定したAPIやユーザーによる実行を提案します。

## 新規作成

- 作成先はユーザーが指定する。既存RG・新規RGの両方に対応する。
- 既存リソースの上書きを避けるため、作成する全リソースのIDを確定して存在確認し、同名があれば停止する。
- 作成コマンド・IaC・費用・依存先・自動実行の有無を提示する。ユーザーが管理権限のある接続で最初の作成を実行する。
- 新しくできたリソースIDだけに専用アプリの必要権限を付与するコマンドを提示する。
- 以降の設定・アプリ配置・検証は専用アプリで実行する。
- App Service等のWrite権限は作成と更新を兼ねるため、「作成だけ」のつもりで既存RG全体に付与しない。
- What-ifは差分確認の補助。未評価の項目や外部への副作用を完全に検知する保証ではない。
- ユーザーが実行するコマンドも、同名確認・具体的な対象・非削除の方式で準備する。人が実行すること自体を安全保証にしない。
- 初回作成時に親プランやStorage等が必要なら、その新規/既存と権限を一緒に提示する。


## Sandboxでの試験

ユーザーはSandboxを動作確認・試験構築に利用できると指定しています。
接続先はPC側のsandboxSubscriptionIdで確認し、明示した対象リソースだけを扱います。
既存本番のキー・接続先・マネージドIDを試験へ安易に流用せず、実データや自動トリガーへの影響を確認します。
試験であっても、RG全体への変更権限、削除、共有リソース変更を自動許可したとは解釈しません。
